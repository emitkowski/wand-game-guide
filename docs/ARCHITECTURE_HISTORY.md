### 2026-07-24 — Chat message ordering via per-conversation locked counter, not DB identity columns
**Decision:** `messages.sequence_number` (authoritative ordering within a conversation) is assigned in application code by incrementing `conversations.last_sequence_number` inside a transaction that takes `lockForUpdate()` on the conversation row — not via a Postgres identity/generated column or a global auto-increment.
**Alternatives considered:** Postgres identity column (`generatedAs()`) on `messages.sequence_number`; a global auto-increment `bigserial` id used directly as the ordering key; Snowflake/HLC-style distributed IDs.
**Reasoning:** This project's test suite runs against SQLite (`phpunit.xml`) while production runs Postgres (AGENTS.md stack line) — DB-native identity columns don't behave identically across both, so the app-level counter was chosen to work the same everywhere. The row lock only serializes writes within one conversation (never across conversations), so it isn't a global bottleneck at scale; a single conversation's write volume doesn't approach what one row lock can't handle. Distributed-ID schemes were rejected as solving a multi-writer-throughput problem this domain doesn't have.
**Consequences:** Any future write path that creates messages (e.g. an internal assistant-reply service) must go through `App\Actions\RecordConversationMessage` — or an equivalent that takes the same lock — rather than inserting into `messages` directly, or ordering guarantees break. See docs/chat-sync-spec.md §4.1 and docs/SCHEMA.md.

### 2026-07-24 — Chat messages are immutable/append-only, no edit or delete path
**Decision:** The `messages` table has no update path for `body` and no delete semantics in the API — messages are write-once. Retraction, if ever needed, should use a tombstone column, not destructive edits.
**Alternatives considered:** Mutable messages with last-write-wins conflict resolution on edits; soft-delete for retraction.
**Reasoning:** An append-only log removes the hardest class of multi-device sync problems (concurrent edit conflicts) entirely, since the only sync question left is ordering of new entries, not merging changes to existing ones. This trade directly shaped the whole sync design in docs/chat-sync-spec.md §4.2.
**Consequences:** A future edit/retraction feature is a schema addition (tombstone or versioning), not a redesign of the sync model — but it is out of scope today, and no code currently depends on messages being mutable.

### 2026-07-25 — Message history query switched to descending order; `next_cursor` is the "load older" token
**Decision:** `GET /api/v1/conversations/{id}/messages` now queries `orderByDesc('sequence_number')->cursorPaginate()` instead of ascending. With no cursor, this returns the most recent messages (previously returned the oldest — see BUG-3, docs/BUGS_ARCHIVE.md). The resource collection's `data` array is reversed for ascending display order without touching the underlying paginator, so `meta.next_cursor` (not `prev_cursor`) is the correct token to request older history with.
**Alternatives considered:** Keeping ascending order and having the client always request the *last* page (requires knowing total count up front, which cursor pagination deliberately avoids); hand-constructing a `Illuminate\Pagination\Cursor` pointing at "the newest end" to feed into an ascending query (verified as possible, but more code and more ways to get the cursor's internal `pointsToNextItems` flag wrong than just flipping the query direction).
**Reasoning:** A chat UI's default view is "show me where the conversation currently stands," not "show me the beginning." Descending-order-with-reversed-output achieves that using cursorPaginate()'s own built-in mechanics for every page (including the first), rather than special-casing the initial request.
**Consequences:** This is now the API's actual contract — any client (this repo's `resources/js/pages/game-guide/Chat.vue`, or a future desktop/overlay client per docs/chat-sync-spec.md) must read `meta.next_cursor` for "load older," not `prev_cursor`. The Redis cache added the same day (docs/chat-sync-spec.md §6) is built on this corrected query, not the buggy one.

### 2026-07-25 — Game Guide's AI replies reuse the sibling "advisor" project's Anthropic integration setup, hardcoded to a single personality
**Decision:** Assistant replies are generated by a direct HTTP integration against Anthropic's Messages API (`App\Services\AnthropicService`), not the `anthropic-ai` SDK or a third-party LLM framework (LangChain, Prism, etc.). The system prompt is a single hardcoded "Game Guide" personality (`App\Actions\GenerateGameGuideReply::SYSTEM_PROMPT`) — no database-backed `Agent` model, no personality switching, no numeric personality-trait scoring. Generation happens in a queued job (`GenerateGameGuideReplyJob`, dispatched from `RecordConversationMessage::record()` only for genuinely new player messages) and persists through a new `RecordConversationMessage::recordAssistantReply()` method — the same locked-counter/cache-invalidation/broadcast path player messages use — fulfilling the internal path docs/chat-sync-spec.md §5 anticipated but deliberately left unbuilt. Gated by a new Pennant flag, `game-guide-ai-replies`, independent of `chat-history-sync`.
**Alternatives considered:** Porting the sibling `advisor` project's full `Agent` model (DB-backed presets, numeric personality-trait block, "algorithm" meta-prompt framework, web search tool, SSE streaming) — rejected as building a multi-persona switching system for an app that only ever needs one hardcoded persona and has no UI for switching agents. A generic LLM abstraction library — rejected; `advisor`'s own direct-HTTP approach was already proven in production and is the explicit pattern this app was asked to reuse.
**Reasoning:** "Reuse the same setup, don't reinvent it" meant matching `advisor`'s actual integration shape (direct Anthropic Messages API calls, ephemeral prompt-caching header, a system-prompt preamble as the personality) while dropping everything in that project which exists only to support *multiple* switchable agents. Generating the reply as a queued side-effect of the player-message write — rather than inline in the request — matches this app's existing "real-time is a queued side effect of a write" pattern (docs/CODE_PATTERNS.md) and means a slow/failed Anthropic call never blocks or fails the player's own message send.
**Consequences:** Any future change to Game Guide's personality is a one-file edit (`GenerateGameGuideReply::SYSTEM_PROMPT`), not a database migration. If multi-persona switching is ever wanted, `advisor`'s `Agent` model/`SystemPromptBuilder` is the reference implementation to port properly at that point — not something to half-build now. Sending player message content to Anthropic's API is a new third-party data flow; see the COMPLIANCE.md addition proposed the same session.

### 2026-07-25 — Confirmed-dead scaffolding deleted outright rather than tested or left as a documented anti-pattern
**Decision:** During a "full testing" pass, ~10 files with zero call sites anywhere in the app were deleted rather than given tests: `app/Utils/ApiResponse/*` (5 files, a never-registered Fractal-based response formatter), `app/Facades/Logger.php` + `app/Utils/Logger/*` (3 files) + `app/Providers/LoggerServiceProvider.php` (also never registered), `app/Models/Traits/Activable.php` (unused by any model), `app/functions.php` (12 helper functions, all with zero call sites — its `composer.json` `autoload.files` entry was removed too). `app/Console/Commands/CommandAbstract.php` and its only subclass `app/Console/Commands/Utility/Test.php` were deleted as a consequence — the abstract class depended on the deleted `CommandLoggerTrait` and would otherwise have been left broken. `app/Jobs/TestFailedJob.php` (dispatched by the now-deleted `utility:test --queue`) and its existing test were left alone — independently valid, not part of the dead chain.
**Alternatives considered:** Writing tests for the dead code anyway, to hit a coverage number without touching production files — rejected as busywork that asserts behavior nothing in the app actually exercises, and leaves confusing, never-imported code sitting in the tree for the next person to wonder about. Leaving it in place as a documented "anti-pattern, don't use this" entry in docs/CODE_PATTERNS.md (the status quo before this decision) — rejected once "zero call sites anywhere" was confirmed by grep; a warning label is for code someone might reach for by mistake, not code that's already completely disconnected from the app.
**Reasoning:** Backend coverage moved from 57.9% to 100.0% immediately on deletion, before a single new backend test was written — the dead files were a large, inert denominator. Confirmed via `grep -rl` across `app/`, `resources/`, `routes/`, `database/`, `config/`, and `tests/` before deleting anything, and cross-checked against `bootstrap/providers.php` (neither `LoggerServiceProvider` nor `ResponseServiceProvider` was registered there). Explicit developer confirmation was obtained before any deletion, per this repo's hard rule on destructive actions.
**Consequences:** `docs/CODE_PATTERNS.md`'s former "Anti-patterns" entries for this code now just point back here — there's nothing left to warn people away from. `docs/COMMANDS.md` no longer needs to explain why `utility:test` doesn't count as a real project command; it simply doesn't exist anymore. Any future logging need uses `Illuminate\Support\Facades\Log` (already this app's real convention); any future API response shaping uses `Illuminate\Http\Resources\Json\JsonResource` (same).
