### BUG-8 — 2026-07-27 — Production queue worker broadcasts hit the wrong host/port (Verified.)
**Was:** `config/broadcasting.php`'s `reverb` connection already overrode `options.host` with `REVERB_CLIENT_HOST` (added for the Docker dev setup, where the queue container reaches Reverb over the internal Docker network — see docs/DOCKER.md) but still read `options.port`/`options.scheme` from the plain `REVERB_PORT`/`REVERB_SCHEME` vars, defaulting to `443`/`https`. Production's `.env` set neither Docker-specific override, so the server-side broadcaster fell back to `https://127.0.0.1:443` — nginx's default vhost on that port — instead of Reverb itself, which is listening in plain HTTP on `127.0.0.1:8082` (confirmed via `ss -tlnp` and a direct `curl` to both addresses; the `/app` nginx location for the real public domain proxies to `http://127.0.0.1:8082`, but the broadcaster never goes through that location — it connects directly by IP/port). Every server-side broadcast (every new chat message, every AI reply) threw `Illuminate\Broadcasting\BroadcastException` with an unrelated site's/nginx's branded 404 HTML page as the "Pusher error" body; discovered when Eric pasted a real production stack trace.
**Fix:** Extended `config/broadcasting.php`'s `reverb` connection to add matching `REVERB_CLIENT_PORT`/`REVERB_CLIENT_SCHEME` overrides (falling back to `REVERB_PORT`/`REVERB_SCHEME` when unset, so the existing Docker setup — where they're already equal — needs no `.env` change), documented in `.env.example`. Production `.env` got `REVERB_CLIENT_PORT=8082`/`REVERB_CLIENT_SCHEME=http` (matching Reverb's actual listening address, confirmed live), config cache cleared/rebuilt, and the `wandgameguide-worker` Supervisor process restarted to pick it up. Verified live (not just via config inspection): dispatched a real `MessageCreated` broadcast event through the production `database` queue after the fix — the worker processed it with zero new `failed_jobs` rows and no new `storage/logs/laravel-2026-07-27.log` entries, versus every prior attempt failing outright.
**Commit/PR:** Uncommitted at time of writing — `config/broadcasting.php`/`.env.example` fixed in the local working tree; production itself was hotfixed out-of-band via direct SSH ahead of any commit, same pattern as BUG-7.

### BUG-10 — 2026-07-27 — Reconnecting after an offline period never fetched messages missed from other sources (Verified.)
**Was:** `Chat.vue`'s `online` browser event only called `flushOutbox()`, which exclusively POSTs this client's own locally-queued outbox entries — it never re-fetched history. The Reverb/Echo WebSocket has no missed-event replay (standard Pusher-protocol behavior): any broadcast that fired while this client was disconnected is gone from that client's perspective once reconnected. `loadInitial()`, the only code path that fetches authoritative history, ran exactly once in `onMounted` and was never re-invoked on reconnect. Net effect: if this client went offline, another source (different device/tab/platform) sent messages during that window, and this client came back online, it correctly flushed its own queued sends but silently never learned about the other source's messages until a manual page reload — a real violation of the explicit product requirement that Game Guide conversations sync seamlessly across devices/platforms/sessions/brief offline periods (see memory: game-guide-sync-requirement).
**Fix:** Added `syncMissedMessages()` to `Chat.vue` — re-fetches the latest history via the same no-cursor endpoint `loadInitial()` uses, merges in any message not already known (by `id` or `client_message_id`, so it never duplicates something already reconciled via the outbox), and stably sorts the result (real `sequence_number`s ascending, any still-unconfirmed local sends kept last in their existing relative order). Wired into the `online` event via a new `handleReconnect()` that calls `syncMissedMessages()` before `flushOutbox()`, replacing the old direct `flushOutbox` listener (and its corresponding `removeEventListener` in `onUnmounted`).
**Commit/PR:** Uncommitted at time of writing. 4 new tests in `resources/js/pages/game-guide/__tests__/Chat.test.ts`: the lock-in test itself ("re-fetches history..."), written as `it.skip` citing BUG-10 first and un-skipped once the fix landed (per this repo's bug-lock-in convention); one confirming a message already reconciled via the outbox isn't duplicated by the sync; and two confirming the sort actually reorders correctly — a synced real message ahead of a still-queued local one, and two already-real messages reordered by `sequence_number`. That last pair caught a real self-inflicted test bug before it landed: the first version of the "reorders two real messages" test relied on `serverMessage()`'s default `client_message_id` fixture value, which both test messages shared unless overridden — the sync's own dedup logic then treated the "missing" message as already-known and never pushed it, yet the assertion (`text.indexOf('First message')).toBeLessThan(text.indexOf('Second message'))`) still passed *vacuously*, since a missing string's `indexOf` returns `-1`, which is `< ` any real found index. Fixed by giving each fixture message a distinct `client_message_id` and adding explicit `toContain()` checks before the ordering comparison (see docs/memory/testing.md's 2026-07-27 entry for the general lesson). Full suite run directly via host `npx vitest` (Docker/Sail unavailable in this session): 223 tests passing, 18 of them in `Chat.test.ts`; lint and `vue-tsc --noEmit` both clean.

### BUG-11 — 2026-07-27 — Reconnect resync only triggered by the browser `online` event, not by the WebSocket's own reconnection (Verified.)
**Was:** Asked directly whether two clients are now guaranteed to align after BUG-10's fix, which surfaced that `syncMissedMessages()` was only ever wired to the browser's `online` event. `navigator.onLine`/`online` reflects the OS's view of the network interface, not the Reverb WebSocket's actual connection state — a WebSocket-level disconnect/reconnect that never toggles the network interface (a Reverb server restart, an idle-timeout drop, laptop sleep/wake without a real network change) never fires `online`, so `handleReconnect()` never ran and any broadcasts missed during that gap were silently lost — the same failure mode BUG-10 fixed for the *offline* case, just via a trigger path that didn't cover every disconnect cause.
**Fix:** Wired `handleReconnect()` to Pusher-js's own `'connected'` event too, via `window.Echo.connector.pusher.connection.bind('connected', handleReconnect)` in `onMounted` (unbound in `onUnmounted`) — this fires on every successful (re)connection regardless of cause, a strictly more reliable signal than the browser-level event for "I might have missed broadcasts."
**Commit/PR:** Uncommitted. New test: "re-syncs when the WebSocket reconnects, even without a browser online event" — dispatches Pusher-js's `connected` callback directly with no `online` event at all. The existing mount/unmount test was also extended to assert `bind`/`unbind` are called with `'connected'`.

### BUG-12 — 2026-07-27 — Reconnect resync only fetched the latest page, silently dropped older missed messages beyond it (Verified.)
**Was:** Same follow-up as BUG-11. `syncMissedMessages()` fetched only the no-cursor default page (`per_page`, currently 50 messages). If a client was disconnected long enough that more than one page's worth of messages arrived from other sources, only the newest 50 got merged in — anything older than that, up to the client's last-known message, was silently skipped with no gap detection at all.
**Fix:** `syncMissedMessages()` now tracks the client's previous highest known `sequence_number` before fetching, and if the newly-fetched page's oldest message isn't contiguous with it, pages backward through the same cursor mechanism `loadOlder()` uses (`docs/CODE_PATTERNS.md`'s cursor-pagination pattern — explicitly designed to serve both "load older" and delta-sync from one mechanism, no new backend endpoint needed) until the gap closes or history runs out, bounded by a new `MAX_BACKFILL_PAGES` constant (20 pages ≈ up to 1,000 messages) to prevent an unbounded fetch loop against a pathological gap. When backfill occurs, `olderCursor.value` is also updated to the new boundary — without this, a subsequent manual "load older" click would re-fetch (and, since `loadOlder()` has no dedup, re-prepend) a page overlapping what backfill just added.
**Commit/PR:** Uncommitted. New test: "backfills older pages when more than one page's worth of messages was missed" — a 3-page gap (sequence 1 already known, page 1 returns sequence 3 with a cursor, backfill page returns sequence 2) resolves into all three messages present and correctly ordered.
**Also found in the course of this fix:** a pre-existing, unrelated test bug in `Chat.test.ts`'s shared `beforeEach` mock — `window.axios.get` used `mockResolvedValue({ data: { data: [] ... } })`, which resolves every call to the *same* array object. Since `loadInitial()` assigns that array directly to `messages.value` (a Vue `ref`), any later `.push()` onto `messages.value` reactively mutated the shared mock array in place — silently contaminating a second `mount()` within the same test that relied on the same default mock without reassigning it. This meant `hydrateOutbox()`'s actual re-add-from-`localStorage` push had never really been exercised by the "persists a queued message across a reload" test — that test was passing because the leftover mutated array made the message look "already fetched," not because of the code path it was meant to verify. Caught via v8 per-statement coverage showing `hydrateOutbox()`'s push as 0 count despite that test passing. Fixed by switching the shared mock to `mockImplementation(() => Promise.resolve({...}))`, which returns a fresh array on every call — see docs/memory/testing.md's 2026-07-27 entry (second one, same date).

**Was:** `.github/workflows/deploy.yml`'s `deploy` job SSH script ran `npm run build` with no `set -e` and no error check, so when the build failed it didn't stop the script — `migrate`/`storage:link`/`optimize:clear`/`optimize` all still ran, `appleboy/ssh-action` reported success, and the whole GitHub Actions run showed ✓. This was the *first* time the `deploy` job had ever actually reached this SSH step (the two prior runs failed in the `test` job on BUG-6, before `deploy`'s `needs: test` let it run), so it was also the first real chance for production's `public/build` assets to refresh since the project's original manual deploy — which predates the passkey-login removal. Confirmed via `gh api repos/.../actions/jobs/89862155498/logs`: Vite failed with two `UNLOADABLE_DEPENDENCY` errors (`resources/js/routes/game-guide`, the `ConversationMessageController` Wayfinder action) because the `@laravel/vite-plugin-wayfinder` Vite plugin logged "Types generated" but hadn't actually finished writing those two generated files to disk before Rolldown tried to resolve them — yet the script sailed past the failure and reported success. Confirmed live on production (`curl` of `/login`) that it still `modulepreload`s a `PasskeyVerify-*.js` chunk, even though `PasskeyVerify.vue` was deleted from the repo and the current `Login.vue` has no passkey import at all.

Also moved `php artisan optimize:clear` to run before `npm ci`/build (was previously after) so a stale cached route list from a prior deploy can never be what Wayfinder generates against. Verified locally: `php artisan route:cache` (to simulate a stale/cold cache) followed by the new script's exact sequence (`optimize:clear` → `wayfinder:generate --with-form` → `npm run build`) builds cleanly with no `PasskeyVerify` reference anywhere in the resulting `public/build/manifest.json`. Then verified for real: with Eric's explicit go-ahead, ran the exact fixed command sequence directly over SSH against the production droplet (`root@64.23.173.119`, per `remote.md`) rather than waiting for a push — build succeeded cleanly (`vite build` completed with no `UNLOADABLE_DEPENDENCY` errors), and a live `curl` of `https://wand-game-guide.ericmitkowski.com/login` afterward confirmed zero occurrences of "passkey" anywhere in the served HTML and the new build's `Login-*.js` chunk hash. Production is fixed as of this run; the `.github/workflows/deploy.yml` change itself is still uncommitted, so a future push should still land it or the same class of failure (silent stale-asset deploy) can recur on the next `npm run build` hiccup.
**Commit/PR:** Uncommitted at time of writing — see `.github/workflows/deploy.yml`. Production itself was fixed out-of-band via direct SSH on 2026-07-27, ahead of any commit.

### BUG-6 — 2026-07-26 — CI test job never built frontend assets, so any test rendering an Inertia page threw `ViteManifestNotFoundException` (Verified.)
**Was:** `.github/workflows/deploy.yml`'s `test` job only set up PHP/Composer before running `php artisan test --compact` — it never ran `npm ci`/`npm run build`, so `public/build/manifest.json` never existed on the CI runner. Any test that renders a real Blade view containing `@vite(...)` (i.e. any Inertia page load — `AuthenticationTest`'s login screen render, `GameGuideControllerTest`'s dashboard render, etc.) threw `Illuminate\Foundation\ViteManifestNotFoundException`, surfacing as a generic 500 in the test's HTTP assertion. **Commit/PR:** Uncommitted at time of writing — see `.github/workflows/deploy.yml`.

### BUG-5 — 2026-07-26 — Test suite silently hit Laravel's log/broadcast emergency fallback on every single run (Verified.)
**Was:** `phpunit.xml` set `<env name="LOG_CHANNEL" value="null"/>` and `<env name="BROADCAST_CONNECTION" value="null"/>`, intending to select the `'null'` channel/connection defined in `config/logging.php`/`config/broadcasting.php` (both silently discard output — the right choice for a test suite). But Laravel's `env()` helper (`Illuminate\Support\Env`) special-cases the literal string `"null"` and converts it to PHP `null` — so `config('logging.default')`/`config('broadcasting.default')` resolved to `null`, not the string `'null'`. `LogManager::resolve()`/`BroadcastManager::resolve()` then failed to find a config entry for an empty channel name and threw `InvalidArgumentException("Log [] is not defined.")` / the broadcasting equivalent. For logging, Laravel's `LogManager::get()` silently catches this internally and falls back to an "emergency" file logger hardcoded to `storage/logs/laravel.log` — so every test run wrote an `EMERGENCY: Unable to create configured logger` line plus the original log message to that file, completely invisibly (no test failure, no visible warning in `artisan test` output) — confirmed present in that file going back to at least 2026-07-25. It only ever fired for `AppServiceProviderTest::test_boot_forces_https_scheme_in_production` (the only test that calls `Log::warning()` from a code path this test suite actually exercises) rather than every `Log::` call in the suite, though the root config defect affected every test uniformly. The broadcasting equivalent never actually threw in practice (0 occurrences ever found in logs) since no test triggers real default-connection broadcast resolution outside `BroadcastAuthorizationTest`, which already explicitly overrides `broadcasting.default` to `'reverb'` — but it was an identical latent defect, one config resolution away from throwing uncaught (no emergency-fallback equivalent exists for broadcasting).
**Fix:** Changed both env values in `phpunit.xml` to `value='"null"'` — wrapping the value in literal double-quote characters, which Laravel's `Env::getEnvironmentVariable()` strips via regex *after* checking for (and skipping, since the quoted form doesn't match) the magic `true`/`false`/`null`/`empty` keywords, preserving the real 4-character string `null`. Verified via a temporary diagnostic test: before the fix, `config('logging.default')`/`config('broadcasting.default')` were `NULL` (PHP null, confirmed with `var_export`); after, both are the string `'null'`. Re-ran the full suite (86 tests) before and after: same pass count both times, but `storage/logs/laravel.log` gained 0 new lines after the fix (previously gained ~22 lines — one full emergency entry — on every single run that included `AppServiceProviderTest`).
**Commit/PR:** Uncommitted at time of writing — see `phpunit.xml`.

### BUG-4 — 2026-07-26 — Burst of player messages could make Game Guide's reply call Anthropic with a trailing assistant turn, which Anthropic rejects outright (Verified.)
**Was:** `GenerateGameGuideReply::generate()` built the Claude `messages` payload from `$conversation->messages()->orderByDesc('sequence_number')->limit(30)->get()->reverse()` — i.e. "whatever the conversation's current tail is" at the moment a given `GenerateGameGuideReplyJob` happened to execute, not a window anchored to the specific player message that job was dispatched for. `RecordConversationMessage::record()` dispatches one job per player message; under bursty send volume, jobs can execute out of order relative to when their triggering message was created. If another job's assistant reply landed as the conversation's current latest message before an earlier-triggered job ran, that job's query window ended in an `assistant`-role turn instead of the `user` turn it was meant to answer. Anthropic's Messages API rejects this outright. Discovered as a side effect of a live rate-limit test (60 rapid player messages), then reproduced directly against the real Anthropic API: `status=400`, body `{"type":"error","error":{"type":"invalid_request_error","message":"This model does not support assistant message prefill. The conversation must end with a user message."}}`. Not an edge case — any player sending two or more messages before Game Guide replies to the first could hit this in production, with no failure signal reaching the client.
**Fix:** `GenerateGameGuideReply::generate(Message $triggeringMessage)` now takes the specific message it's replying to (previously `Conversation` + `OriginPlatform`) and anchors the history query with `where('sequence_number', '<=', $triggeringMessage->sequence_number)`, guaranteeing the window always ends with the exact user turn this job was dispatched to answer regardless of what other jobs have done since. `GenerateGameGuideReplyJob` now carries the triggering `Message` instead of `Conversation`+`OriginPlatform`; `RecordConversationMessage::record()` dispatches it with the newly-created message directly. Also fixed `AnthropicService`'s failure logging, which only captured the HTTP status — now also logs `error.type`/`error.message` from Anthropic's response body (safe to log: it's Anthropic's own error metadata, not player message content, so `docs/COMPLIANCE.md`'s body-content restriction doesn't apply), since the status-only log was what made this bug take real reproduction work to root-cause instead of reading it straight from the logs. Verified two ways: the previously-skipped lock-in test (`GenerateGameGuideReplyTest::test_reply_generation_never_sends_a_trailing_assistant_turn_to_claude`) now passes for real, and the exact live failing scenario (triggering message at sequence 1 while the conversation's real tail was at sequence 62) was re-run against the real Anthropic API and now succeeds.
**Commit/PR:** Uncommitted at time of writing — see `app/Actions/GenerateGameGuideReply.php`, `app/Jobs/GenerateGameGuideReplyJob.php`, `app/Actions/RecordConversationMessage.php`, `app/Services/AnthropicService.php`.

### BUG-3 — 2026-07-25 — Chat history endpoint returned oldest messages first, not most recent (Verified.)
**Was:** `ConversationMessageController::index()` queried `orderBy('sequence_number')->cursorPaginate()` (ascending). With no cursor, cursor pagination returns the *first* page — for a conversation longer than the page size, opening the chat would show the oldest messages in the conversation instead of the latest ones, which is wrong for a chat UI's "open and see recent context" case. Found via code review while building the Redis cache, which needed to cache the correct "latest messages" query.
**Fix:** Switched the query to `orderByDesc('sequence_number')->cursorPaginate()` (most recent N with no cursor), then reversed only the resource collection's `data` array for ascending display order — verified against Laravel's pagination source that `nextCursor()`/`previousCursor()` are computed lazily from the paginator's own untouched item list, so reversing just the mapped output doesn't corrupt cursor correctness. `meta.next_cursor` is now the "load older" token (previously `prev_cursor`); `resources/js/pages/game-guide/Chat.vue` updated to match.
**Commit/PR:** Uncommitted at time of writing — see `app/Http/Controllers/Api/V1/ConversationMessageController.php`.

### BUG-1 — 2026-07-25 — Private user channel authorization always passed (Verified.)
**Was:** `routes/channels.php`'s `Broadcast::channel('App.Models.User.{id}', ...)` compared `(int) $user->id === (int) $id`. `User` uses `HasUuids`, so `id` is a UUID string; casting any UUID string to `int` yields `0` on both sides, meaning the check always evaluated true regardless of which user was asking — any authenticated user could subscribe to any other user's private channel.
**Fix:** Changed to a direct string comparison, `$user->id === $id`. Verified with `tests/Feature/BroadcastAuthorizationTest.php`, which also covers the `conversation.{id}` channel added alongside the chat-sync work. Confirming this test actually exercised the real callback (not just any 403) took real debugging: this project's tests default to `BROADCAST_CONNECTION=null` (phpunit.xml), whose `NullBroadcaster::auth()` always authorizes without ever invoking registered channel callbacks — the test switches to the `reverb` driver and re-`require`s `routes/channels.php` so registrations attach to that connection instead of the one resolved at boot. See docs/memory/laravel.md for the full writeup of that gotcha.
**Commit/PR:** Uncommitted at time of writing — see `routes/channels.php`, `tests/Feature/BroadcastAuthorizationTest.php`.

### BUG-2 — 2026-07-25 — deploy.yml CI test job ran against MySQL, a third database engine nobody else uses (Verified.)
**Was:** `.github/workflows/deploy.yml`'s `test` job spun up a MySQL service and set `DB_CONNECTION=mysql` as step-level env for both a "Run migrations" step and the "Run tests" step. `phpunit.xml`'s `<env name="DB_CONNECTION" value="sqlite"/>` has no `force="true"`, so a real shell-level env var (as CI sets) wins over it — meaning CI's test run genuinely executed against MySQL, while local/manual test runs use SQLite (`:memory:`, via `RefreshDatabase`) and production uses Postgres. Also fixed the trigger branch (`master` → `main`) as part of the earlier deploy-wiring work in this same file.
**Commit/PR:** Uncommitted at time of writing — see `.github/workflows/deploy.yml`.
